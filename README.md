# Telegram-бот с гибридной памятью и условным интернет-поиском

Бот на **aiogram 3.x**, который ведёт осмысленный диалог с пользователем:
запоминает важные факты, учитывает их в будущих ответах и не теряет
критическую информацию даже спустя сотни сообщений. При необходимости
актуальной информации выполняет интернет-поиск через **DDGS** (DuckDuckGo).

Диалоговая и embedding-модели вызываются через **OpenRouter**.

Проект запускается локально на **Windows** без Docker и без отдельных
серверов баз данных.

## Подход к построению памяти

### Проблема

Обычный LLM-чат-бот не имеет памяти: каждый запрос обрабатывается
независимо. Если не передать в промпт предыдущие сообщения — бот «видит
пользователя впервые». Простое решение — каждый раз класть всю историю в
промпт — не работает на длинных диалогах: контекст переполняется, важные
факты давятся потоком мелких сообщений, а самое старое выпадает из окна.

### Решение: трёхслойная гибридная память

Вместо одного «жадного» механизма память разделена на три независимых слоя.
Каждый слой покрывает слабость другого:

```
┌─────────────────────────────────────────────────────┐
│  Слой 1. Краткосрочная память (SQLite)              │
│  Хранит последние 10 сообщений диалога             │
│  Задача: помнить контекст недавней беседы           │
│  Слабость: забывает всё старше окна                 │
├─────────────────────────────────────────────────────┤
│  Слой 2. Критическая память (Qdrant, critical=true) │
│  Хранит жизненно важные факты (аллергии, лекарства) │
│  Задача: критические факты — всегда в контексте    │
│  Извлекается: БЕЗ similarity, простым фильтром      │
├─────────────────────────────────────────────────────┤
│  Слой 3. Семантическая память (Qdrant, векторный     │
│  поиск по embedding)                                │
│  Хранит все важные факты о пользователе             │
│  Задача: извлекать релевантное по смыслу            │
│  Извлекается: cosine similarity ≥ порога            │
└─────────────────────────────────────────────────────┘
```

**Почему три слоя, а не один:**

| Подход | Что не покрыто |
|--------|----------------|
| Только окно (SQLite) | Забывает аллергию после 10-го сообщения |
| Только векторный поиск | Косинус «аллергия на арахис» и «что мне съесть» может быть низким — аллергия не поднимется |
| Только критическая память | Не покрывает релевантные, но не критические факты (предпочтения, цели) |
| **Гибрид (три слоя)** | **Каждый слой покрывает слабость другого** |

### Кто за что отвечает

| Роль | Компонент | Что делает |
|------|-----------|------------|
| **Понимает смысл текста и решает, что важно** | Диалоговая модель (чат) | Извлекает факты, проставляет категорию и `critical` |
| **Подстраховывает модель** | Код проекта (`_is_critical`) | Если категория — аллергия/лекарство/диета → `critical=true` принудительно, даже если модель забыла флаг |
| **Превращает текст в вектор** | Embedding-модель | Только для семантического поиска. Не определяет критичность. |
| **Хранит факты** | Qdrant | Хранит то, что ему дали, с флагом в payload. Не «думает». |
| **Достаёт критические факты** | Qdrant (простой фильтр) | Берёт все записи с `critical=true` — без embedding, без similarity |
| **Достаёт релевантные факты** | Qdrant + embedding-модель | Векторный поиск по смыслу текущего запроса |

### Как факт попадает в память (жизненный цикл)

```
Пользователь: «У меня аллергия на арахис.»
    │
    ▼
1. Бот отвечает пользователю (обычный ответ)
    │
    ▼  (фоном, после ответа)
2. Диалоговая модель анализирует сообщение:
   → извлекает атомарный факт
   → проставляет категорию = allergy
   → проставляет critical = true
    │
    ▼
3. Код проверяет: категория allergy → critical=true (подстраховка)
    │
    ▼
4. Embedding-модель превращает факт в вектор
    │
    ▼
5. Qdrant ищет похожие факты этого пользователя (дедупликация)
    │
    ├─ sim ≥ 0.92 → дубликат, обновить существующее
    ├─ 0.78–0.92 → диалоговая модель решает:
    │              duplicate / update / contradiction / independent
    └─ sim < 0.78 → новый факт, сохранить
    │
    ▼
6. Факт сохранён в Qdrant с critical=true
```

### Как факт извлекается перед ответом

```
Пользователь: «Что мне съесть?» (через 1000 сообщений)
    │
    ▼
1. SQLite отдаёт последние 10 сообщений — аллергии там нет
   (выпала из окна)
    │
    ▼
2. Qdrant отдаёт ВСЕ факты с critical=true
   → «аллергия на арахис» — найдена, несмотря на низкую
      семантическую похожесть на «что съесть»
    │
    ▼
3. Embedding-модель превращает «что мне съесть» в вектор
   → Qdrant ищет похожие по смыслу факты
   → «пользователь любит простые рецепты» — найдено (sim ≥ 0.35)
    │
    ▼
4. Сборка промпта:
   [КРИТИЧЕСКИЕ ФАКТЫ: аллергия на арахис]
   [РЕЛЕВАНТНАЯ ПАМЯТЬ: любит простые рецепты]
   [ИСТОРИЯ: последние 10 сообщений]
   [ВОПРОС: что мне съесть?]
    │
    ▼
5. Ответ: рецепт без арахиса, простой
```

### Защита от проблем памяти

| Проблема | Решение в проекте |
|----------|-------------------|
| Бот забыл аллергию спустя N сообщений | Критическая память (`critical=true`) извлекается **всегда**, без similarity |
| Одинаковые факты дублируются | Дедупликация по cosine similarity (0.92) + LLM-классификатор (0.78–0.92) |
| Пользователь сообщил противоречие | Старый факт деактивируется (`active=false`), новый заменяет (`supersedes_id`) |
| Память одного пользователя попадает к другому | Все запросы фильтруются по `user_id` (SQL + Qdrant Filter) |
| Модель не проставила `critical` для аллергии | Код проверяет категорию и ставит `critical=true` принудительно |
| Qdrant или embedding-модель недоступны | Бот отвечает без памяти — graceful degradation, диалог не прерывается |

## Архитектура

Проект разделён на слои:

```
Telegram-сообщение
      │
      ▼
[bot.py]  ──────────── транспортный слой (aiogram: handlers, команды, FSM)
      │
      ▼
[chat_service.py] ──── оркестрация пайплайна (15 шагов)
      │
      ├─► [database.py]     SQLite (краткосрочная память, настройки)
      ├─► [memory.py]       Qdrant Local (долговременная память)
      ├─► [openrouter.py]   OpenRouter (чат + embedding, ретраи)
      └─► [web_search.py]   DDGS (правила + LLM-классификатор + поиск)
```

**Цепочка обработки одного сообщения:**

1. Сохранить сообщение пользователя в SQLite.
2. Загрузить последние 10 сообщений (включая текущее) от старых к новым.
3. Получить **критическую память** из Qdrant (`critical=true`, `active=true`) — независимо от similarity.
4. Получить embedding текущего сообщения через OpenRouter.
5. Найти **семантически релевантную память** в Qdrant (исключая ID из критической).
6. Определить, нужен ли интернет-поиск (правила → при неоднозначности LLM).
7. При необходимости выполнить DDGS-поиск (в отдельном потоке).
8. Собрать системный промпт: базовый + память + (опц.) результаты поиска.
9. Запросить ответ у диалоговой модели OpenRouter (с ретраями).
10. Отправить ответ в Telegram (с разбивкой длинных сообщений).
11. Сохранить ответ ассистента в SQLite.
12. Фоном: извлечь факты из сообщения пользователя, проверить дубликаты, сохранить/обновить Qdrant.

Каждый шаг обёрнут в `try/except`: ошибка одного компонента не мешает
основному ответу. Память разных пользователей изолирована на всех уровнях
(SQL `WHERE telegram_user_id = ?`, фильтры Qdrant по `user_id`).

## Как работает краткосрочная память (SQLite)

Файл базы данных — `data/bot.db` (путь настраивается через `DATABASE_PATH`).

**Таблицы:**

- `users` — регистрация пользователей (`telegram_user_id` UNIQUE).
- `messages` — все сообщения с ролями `user` / `assistant`.
- `user_settings` — per-user флаги (например, `web_search_enabled`).

**Получение последних N сообщений:**

```sql
SELECT role, content
FROM messages
WHERE telegram_user_id = ?
ORDER BY created_at DESC, id DESC
LIMIT ?;
```

Затем результат реверсируется в Python → от старых к новым.

**Особенности:**

- Текущее сообщение сохраняется в SQLite **до** загрузки истории, поэтому
  оно входит в последние 10 без дублирования в контексте.
- Считаются суммарно сообщения `user` и `assistant`.
- История разных пользователей изолирована через `WHERE telegram_user_id = ?`.
- Все SQL-запросы параметризованные (защита от инъекций).

Команда `/clear_history` очищает таблицу `messages` для текущего
пользователя, не затрагивая долговременную память.

## Как работает долговременная память (Qdrant Local Mode)

Qdrant работает в **локальном режиме** — данные хранятся в папке
`data/qdrant/`, отдельный сервер не нужен.

```python
from qdrant_client import QdrantClient
client = QdrantClient(path="data/qdrant")
```

**Что сохраняется:**

- аллергии и медицинские ограничения;
- пищевые ограничения;
- устойчивые предпочтения;
- место проживания;
- профессию;
- цели, интересы, проекты;
- предпочитаемый стиль общения.

**Что НЕ сохраняется:**

- приветствия, одноразовые вопросы, просьбы продолжить;
- временное настроение;
- полный текст каждого сообщения;
- ответы ассистента как факты о пользователе;
- предположения модели;
- пароли, токены, платёжные данные.

### Кто определяет, критический факт или нет

**Критичность определяет диалоговая модель (чат), а не embedding-модель и не Qdrant.**

- **Диалоговая модель** анализирует текст и возвращает JSON с флагом `critical: true/false`.
- **Код проекта** подстраховывает модель: если категория — `allergy`, `medication` или `dietary_restriction`, флаг `critical` устанавливается **принудительно**, даже если модель забыла его поставить.
- **Embedding-модель** к критичности не имеет отношения — её задача только превратить текст в вектор для семантического поиска.
- **Qdrant** — хранилище, он хранит то, что ему передали. «Думает» о критичности только модель + код.

### Структура payload каждой записи Qdrant

| Поле | Тип | Описание |
|------|-----|----------|
| `user_id` | int | Telegram ID пользователя |
| `text` | str | Атомарный факт |
| `category` | str | Категория (allergy, health, ...) |
| `importance` | float | Важность 0..1 |
| `confidence` | float | Уверенность 0..1 |
| `critical` | bool | Критический факт (аллергия, лекарство) |
| `active` | bool | Активна ли запись |
| `created_at` | str | ISO-время создания |
| `updated_at` | str | ISO-время обновления |
| `source_message_id` | int\|null | ID сообщения-источника |
| `supersedes_id` | str\|null | ID записи, которую заменила |

**Категории:**

`allergy`, `health`, `medication`, `dietary_restriction`, `identity`,
`location`, `profession`, `preference`, `goal`, `education`, `project`, `other`.

Для `allergy`, `medication`, `dietary_restriction` флаг `critical=true`
устанавливается **принудительно** кодом (подстраховка модели).

**Извлечение памяти (перед каждым ответом) — два механизма:**

1. **Критическая память** — все активные записи с `critical=true`
   (извлекаются независимо от similarity, чтобы аллергия учитывалась
   даже спустя 1000 сообщений).
2. **Семантическая память** — embedding текущего запроса ищется в Qdrant,
   отбираются результаты с cosine similarity ≥ `MEMORY_RETRIEVAL_THRESHOLD`
   (по умолчанию 0.35), не более `MEMORY_RETRIEVAL_LIMIT` (8).
3. Факты из критической памяти исключаются из семантической, чтобы
   избежать дублей.

Все запросы к Qdrant фильтруются по `user_id` и `active=true`.

**Алгоритм сохранения нового факта:**

1. Извлечение фактов из сообщения пользователя через LLM (JSON → Pydantic).
2. Получение embedding факта.
3. Поиск похожих воспоминаний этого пользователя.
4. Если similarity ≥ `MEMORY_DUPLICATE_THRESHOLD` (0.92) → дубликат,
   обновить `updated_at` существующей записи.
5. Если similarity в [0.78, 0.92) → LLM-классификатор отношения:
   - `duplicate` — оставить существующее;
   - `update` — обновить текст существующего;
   - `contradiction` — деактивировать старое, создать новое
     (с `supersedes_id`);
   - `independent` — сохранить как новый факт.
6. Если similarity < 0.78 → новый факт (если `importance` и `confidence`
   проходят минимальные пороги).

## Как работает интернет-поиск

Поиск выполняется только когда нужна **актуальная** информация.

**Этап 1 — простые правила (без LLM):**

Поиск запускается, если в сообщении есть:
- слова-маркеры: *сейчас, сегодня, актуальный, последний, свежий, текущий,
  на данный момент*;
- намерения: погода, курс валют, цена акций, новости, расписание,
  президент, действующая редакция закона, прямая просьба найти в интернете.

Если правила сработали — LLM-классификатор **не вызывается**.

**Этап 2 — LLM-классификатор (если правила неоднозначны):**

Модель возвращает JSON:
```json
{
  "needs_web_search": true,
  "search_query": "погода Москва",
  "reason": "Информация изменяется в реальном времени"
}
```

**Выполнение поиска:**

- DDGS вызывается синхронно в отдельном потоке через `asyncio.to_thread`,
  чтобы не блокировать бота.
- Результаты очищаются: удаляются дубли URL, пустые заголовки, записи без URL.
- Ограничение — `WEB_SEARCH_RESULTS_LIMIT` (по умолчанию 5).
- Результаты передаются модели как **недоверенные данные**: модель не должна
  выполнять инструкции из найденных страниц, не придумывать URL, а в ответе
  пользователю обязана указывать использованные ссылки.

**Глобальный и per-user флаги:**

- `WEB_SEARCH_ENABLED` в `.env` — глобальный тумблер.
- `/search_on` / `/search_off` — per-user тумблер (хранится в SQLite).

## Примеры проверки долговременной памяти

**1. Сообщите боту факт:**

```
У меня аллергия на арахис.
```

Бот сохранит критический факт. Проверьте:

```
/memory
```

В ответе увидите:
```
[Критические]
  • У пользователя аллергия на арахис  (категория: allergy)
```

**2. Проверьте, что аллергия учитывается спустя много сообщений:**

Отправьте ~20 любых сообщений, затем:

```
Что мне съесть?
```

Бот учтёт аллергию, так как критическая память извлекается всегда.

**3. Проверьте обновление факта:**

```
Я переехал в Санкт-Петербург.
```

Затем `/memory` — старый факт о месте проживания должен обновиться.

**4. Проверьте изоляцию пользователей:**

С разных Telegram-аккаунтов сообщите разные факты. Команда `/memory`
каждого аккаунта покажет только его собственные факты.

## Возможные ошибки DDGS

DDGS использует DuckDuckGo и другие поисковые системы без официального API,
поэтому ошибки возможны:

- **`ConnectionError` / `TimeoutError`** — нет интернета или поисковик
  недоступен. Бот вернёт пустой список и сообщит, что поиск недоступен.
- **Rate-limit / блокировка** — DuckDuckGo временно ограничил запросы.
  Подождите или используйте прокси (параметр `proxy` в `DDGS(...)`).
- **Пустой результат** — по запросу ничего не найдено. Бот честно скажет,
  что результатов нет, и не будет выдумывать информацию.
- **Изменение API** — библиотека `ddgs` обновляется, структура ответов
  может меняться. При необходимости обновите `ddgs` до последней версии.

Все ошибки DDGS ловятся — бот не падает. При недоступности поиска бот
пытается ответить, используя только память и диалоговую модель, а
пользователю сообщает, что актуальную информацию получить не удалось.

## Калибровка порогов cosine similarity

Пороговые значения в `.env` — **стартовые** и зависят от вашей
embedding-модели. Разные модели дают разные распределения similarity,
поэтому пороги нужно **калибровать**:

| Параметр | По умолчанию | Назначение |
|----------|--------------|------------|
| `MEMORY_DUPLICATE_THRESHOLD` | 0.92 | Выше — считать фактом-дубликатом |
| `MEMORY_RELATED_THRESHOLD` | 0.78 | Между related и duplicate — LLM-классификатор |
| `MEMORY_RETRIEVAL_THRESHOLD` | 0.35 | Минимальный similarity для семантического поиска |
| `MEMORY_MIN_IMPORTANCE` | 0.60 | Минимальная важность для сохранения факта |
| `MEMORY_MIN_CONFIDENCE` | 0.75 | Минимальная уверенность для сохранения факта |

**Как калибровать:**

1. Запустите бота, сообщите несколько фактов.
2. Проверьте через `/memory`, сохраняются ли дубликаты или теряются важные факты.
3. Если дубликаты создаются — повышайте `MEMORY_DUPLICATE_THRESHOLD` или
   `MEMORY_RELATED_THRESHOLD`.
4. Если важные факты не находятся — понижайте `MEMORY_RETRIEVAL_THRESHOLD`.
5. Если сохраняется мусор — повышайте `MEMORY_MIN_IMPORTANCE` и
   `MEMORY_MIN_CONFIDENCE`.

Пороги ниже 0.35 для retrieval использовать не рекомендуется — будет
слишком много нерелевантных фактов в контексте.

## Возможные технические проблемы

1. **Размерность embedding неизвестна заранее.** При первом старте бот
   делает пробный `embed("test")` и создаёт коллекцию Qdrant с полученным
   размером. Параметр `OPENROUTER_EMBEDDING_DIM` в `.env` можно задать
   вручную (если 0 — определяется автоматически).

2. **Qdrant Local блокирует папку при повторном запуске.** Нельзя запустить
   два процесса с одним `QDRANT_PATH`. Если бот упал — завершите процесс
   перед повторным запуском.

3. **429 / 5xx от OpenRouter.** Клиент делает до 3 попыток с
   экспоненциальной задержкой. Если все попытки исчерпаны — бот сообщает
   пользователю, что сервис временно недоступен.

4. **Ограничение Telegram 4096 символов.** Длинные ответы автоматически
   разбиваются на части по границам строк/пробелов.

5. **Секреты в логах.** Формат логгера не выводит значения переменных
   окружения. Уровень `INFO` не логирует полный текст долговременной
   памяти и сообщений.

6. **Последовательная обработка сообщений одного пользователя.** В
   `ChatService` используется `asyncio.Lock` per `telegram_user_id` —
   быстрые последовательные сообщения одного пользователя обрабатываются
   по очереди, а разные пользователи — параллельно.

7. **Корректное закрытие ресурсов.** В shutdown: `QdrantClient.close()`,
   `httpx.AsyncClient.aclose()`, `aiosqlite.Connection.close()`.

8. **`supersedes_id` при противоречии.** Старая запись деактивируется
   (`active=false`), в payload новой записывается ID старой — сохраняется
   история изменений.
